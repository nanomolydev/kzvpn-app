# kzvpn

Один файл: `kzvpn.py`. Ставит системный TUN, весь трафик уходит в туннель,
управление — иконка в трее, live-логи — в браузере.

Сервера задаются vless-ссылками, менять код не нужно:

```bash
./kzvpn.py --hop2 --url "vless://...#мой-сервер"    # свой выходной сервер
./kzvpn.py --url1 "vless://..." --url "vless://..." # своя цепочка целиком
```

Парсер понимает reality и tls, транспорты tcp, xhttp, ws, httpupgrade, grpc,
и сам резолвит домен в IP для правила обхода TUN.

```bash
chmod +x kzvpn.py
./kzvpn.py            # цепочка Обход#4 -> kzVPN, трей
./kzvpn.py --hop2     # только kzVPN  (рабочий режим, см. ниже)
./kzvpn.py --hop1     # только Обход #4
./kzvpn.py --console  # без трея, логи в терминале
```

Работает на Linux, Windows и macOS. Нужен только python3. Xray и sing-box скачиваются сами в `~/.local/share/kzvpn/bin`.
Для TUN нужен root — скрипт сам зовёт `sudo` (или `pkexec`, если запущен не из терминала).
Трею нужны `pystray`+`pillow` (скрипт ставит их себе в venv сам) и системный AppIndicator:

```bash
sudo apt install python3-gi gir1.2-ayatanaappindicator3-0.1
```

GNOME на Wayland вдобавок требует расширение AppIndicator/KStatusNotifier.
Если трея нет — скрипт не падает, а сам уходит в консольный режим и пишет,
чего не хватает; туннель при этом работает, логи в терминале и в браузере.

Live-логи всегда доступны на <http://127.0.0.1:8964/>.

## Windows

```
python kzvpn.py --hop2
```

Xray, sing-box и `wintun.dll` (без неё TUN на Windows не поднимется) качаются
сами в `%LOCALAPPDATA%\kzvpn`. `wintun.dll` берётся прямо из архива Xray — сайт
`wintun.net` у части провайдеров режется, а там ровно та же dll.

Версии закреплены вместе с SHA256 каждого архива (хэши Xray сверены с его
официальными `.dgst`). Если Python не может проверить TLS-сертификат — антивирус
подменяет сертификаты или у Python нет корневых, ошибка `CERTIFICATE_VERIFY_FAILED` —
скрипт качает без проверки TLS, но подменённый или битый файл отвергается по хэшу.

TUN требует прав администратора — запускай
консоль от имени администратора, иначе скрипт скажет об этом и остановится.
Права не нужны для `--check` и `--lan`.

Если на Windows уже запущен другой VPN-клиент со своим TUN, выключи его:
два TUN-интерфейса дерутся за маршрут по умолчанию.

## macOS

`kzVPN-arm64.dmg` (M1 и новее) или `kzVPN-x86_64.dmg` (Intel) собирает GitHub Actions
(`.github/workflows/macos.yml`) на каждый push: вкладка Actions → последний запуск →
Artifacts. Открыть dmg, перетащить kzVPN в «Программы», запустить.

Приложение без подписи Apple, поэтому при первом запуске macOS его не пустит:
Системные настройки → Конфиденциальность и безопасность → «Всё равно открыть».
Или один раз в терминале: `xattr -dr com.apple.quarantine /Applications/kzVPN.app`.
Убрать этот шаг совсем можно только подписью и нотаризацией платным аккаунтом
Apple Developer.

Значок живёт в строке меню. При подключении macOS спросит пароль администратора —
TUN без root не поднять. Отключение пароль не спрашивает, а если приложение
закрыть или оно упадёт, VPN снимается сам. Xray и sing-box при первом запуске
качаются в `~/Library/Application Support/kzvpn` с проверкой SHA256.

В `.app` нельзя передать флаги, так что режим — цепочка по умолчанию.

собранное приложение (`--check --hop2`: скачивание, хэши, туннель), а root-оболочка
TUN проверена тестом без macOS. TUN на Маке и окно пароля проверит только первый запуск.

## Телефон

`--lan` не поднимает TUN, а отдаёт socks5 в локальную сеть — телефон ходит
через этот компьютер с уже работающей нарезкой, настраивать на телефоне
ничего не нужно:

```bash
./kzvpn.py --lan --hop2
```

Скрипт напечатает два адреса:

* `192.168.х.х:10808` — socks5, для Android;
* `192.168.х.х:10809` — http-прокси, для iPhone: Настройки -> Wi-Fi -> сеть ->
  «Прокси» -> «Вручную», сервер и порт отсюда. Приложение не нужно вообще.

Прокси открыты всем в этой сети и без пароля, так что в публичном Wi-Fi
так делать не надо.

Если хочется независимости от компьютера — на телефоне нужен клиент с нарезкой
именно на уровне TLS-записей (движок Xray, `packets: tlshello`): на Android это
v2rayNG, на iOS — Streisand или V2Box. Клиенты на sing-box режут поток по TCP,
а такой вариант замерен как нерабочий (0/10): сниффер собирает его обратно.

## Как устроена цепочка

Два независимых процесса Xray, конфиги друг с другом не смешаны:

1. **первый VPN** — «Обход #4» как есть, поднимает свой socks на `127.0.0.1:10801`;
2. **второй VPN** — kzVPN как есть, весь свой интернет берёт из socks первого;
3. sing-box заворачивает систему в TUN и отдаёт трафик второму.

sniffing на socks первого выключен намеренно: с `destOverride` Xray подменил бы
IP второго сервера на домен из его SNI и ушёл бы на настоящий max.ru.

## Состояние цепочки: работает, но нестабильно (~40%)

Двойной туннель собирается и даёт IP kzVPN — но переживает примерно 4 коннекта
из 10, остальные виснут на таймауте. Для повседневной работы бери `--hop2`.

## Почему так

Сервер «Обход #4» (46.243.234.117) игнорирует IP назначения и переподключает
соединение по домену, вынюханному из SNI. Доказательство:

* напрямую в `5.129.223.183:443` с SNI `ya.ru` → соединение приходит на REALITY-сервер,
  тот отдаёт сертификат `*.max.ru`, curl падает (rc=60) — адрес соблюдён;
* через «Обход #4» тот же запрос на тот же IP → **HTTP 302 с настоящим сертификатом ya.ru**,
  то есть сервер увёл соединение на настоящий ya.ru.

Поэтому когда второй VPN звонит на kzVPN (SNI `max.ru`), сервер уводит соединение
на настоящий max.ru, REALITY видит подлинный сертификат и рвёт связь:
`REALITY: received real certificate (potential MITM or redirection)`.

Это не зависит от способа связки. Проверены все три:
одним процессом через `dialerProxy`, двумя процессами через socks,
и обратный порядок (kzVPN -> Обход#4) — результат одинаковый.
В логах первого процесса видно, что он отдаёт наружу именно
`accepted tcp:5.129.223.183:443 [relay-in >> hop1]` — то есть IP,
без всякой подмены с нашей стороны. Подменяет удалённый сервер.

### Чем это обходится

Единственный клиентский рычаг — резать ClientHello на куски, чтобы сниффер
не собрал из него домен (`FRAGMENT` в начале файла). Это включено в режиме
цепочки по умолчанию и снимает подмену полностью: `received real certificate`
в логах больше нет.

Но за это платим стабильностью. Замеры на живых серверах, по 10 коннектов
последовательно:

| что | успешно |
|---|---|
| только Обход#4 | 10/10 |
| только kzVPN | 10/10 |
| только kzVPN из сети с DPI, без нарезки | 0/5 |
| только kzVPN из сети с DPI, с нарезкой | работает |
| фрагментация поверх Обход#4 на обычный сайт | 10/10 |
| цепочка, fragment `30-50` | 4/10 |
| цепочка, fragment `60-80` | 1/10 |
| цепочка, fragment `100-100` | 0/10 |
| цепочка без фрагментации | 0/10 |

То есть сама нарезка через первый сервер проходит идеально — спотыкается
рукопожатие REALITY второго, когда ClientHello приходит несколькими TLS-записями.
Режим `tlshello` при этом обязателен: raw-нарезка (`packets: "1-2"` и т.п.)
сниффер спокойно собирает обратно, и подмена возвращается.

Mux, который сделал бы рукопожатие одноразовым, недоступен: сервер kzVPN требует
`xtls-rprx-vision` (без flow он отвечает отказом, проверено 0/5), а vision с mux
несовместим.

### Настоящее лечение

На сервере «Обход #4» в его inbound у `sniffing` поставить `"routeOnly": true`
(или выключить sniffing) — тогда домен используется только для правил
маршрутизации, а соединение идёт на исходный IP. После этого цепочка станет
стабильной, и фрагментацию можно будет убрать.

## Проверка

```bash
./kzvpn.py --check          # поднять только туннель, 5 раз спросить внешний IP
./kzvpn.py --check --hop2   # то же для одиночного режима
python3 test_kzvpn.py       # конфиги всех режимов скармливаются живым xray/sing-box
```

Нарезка ClientHello включена во всех режимах: без неё DPI у провайдера глотает
рукопожатие (TCP до сервера открывается за 0.2 с, а попытки виснут до таймаута —
проверено на живой сети, где `--nofrag` даёт 0/5, а нарезка сразу работает).
Там, где DPI нет, она ничего не портит: 5/5 в обоих случаях. Выключается `--nofrag`.

`--check` не трогает TUN и не требует root: он поднимает Xray, пять раз ходит
за внешним IP и в конце печатает последние ошибки из логов. Если `--check`
показывает рабочий IP, а с TUN интернета нет — проблема в маршрутизации,
а не в туннеле.
